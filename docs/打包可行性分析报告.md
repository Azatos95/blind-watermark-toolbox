## 四、打包必须解决的 3 个"坑"（已全部在原型里修掉）

### 坑 1：`cv2.imread/imwrite` 不支持中文路径 ⚠️ 最致命
`blind_watermark` 内部直接用 `cv2.imread`。而 OpenCV 在 Windows 上**遇到非 ASCII 路径直接返回 None**，随后 `assert img is not None` 报错。
你现在的代码放在 `C:\Users\A\Desktop\图片盲水印\...`，如果用户选中文文件名/中文目录（中文用户几乎必然），**功能当场失效**。

我在测试时亲眼复现了这个现象（第一次运行 `AssertionError: image file '...\ͼƬäˮӡ\...' not read`）。

**修法**（原型已实现，`bwm_gui.py` 里 `imread_unicode` / `imwrite_unicode` / `patch_cv2_unicode`）：
用 `np.fromfile()` 读字节流 → `cv2.imdecode()` 解码；写出用 `cv2.imencode()` → `buf.tofile()`。
并把 `cv2.imread/imwrite` 整体替换，这样 blind_watermark 内部调用也自动获得中文支持。

### 坑 2：错误密码会让程序崩溃，而不是"提取失败"
`blind_watermark.py` 第 106 行：

```python
wm = bytes.fromhex(hex(int(byte, base=2))[2:]).decode('utf-8', errors='replace')
```
密码或 `wm_shape` 不对时，这行会抛 `ValueError: fromhex() arg must contain an even number of hexadecimal digits`（我已实测复现）。

**修法**：在 GUI 层 `try/except` 兜住，转成友好提示"密码或水印长度不正确"。原型已这样做。

### 坑 3：输出必须是无损格式（PNG/BMP/TIFF）
算法把 1 bit 藏在小波 DCT 后的 SVD 奇异值里（`d1=36` 的量化步长），**JPEG 有损压缩会直接抹掉水印**，且 PNG 默认无损。
原型会检查扩展名，若不是无损格式就自动改成 `.png` 并提示用户。

> 附带小坑：`WaterMark(...)` 每次构造都会打印欢迎横幅。打包成 GUI 后需要 `blind_watermark.bw_notes.close()` 关掉（原型已处理），否则会污染界面/日志。

## 五、算法本身的硬约束（做产品时必须让用户知道）

这些不是打包问题，但决定了产品能宣称什么、不能宣称什么：

| 约束 | 具体数值/表现 |
|---|---|
| **不可见性 vs 鲁棒性** | 靠 `d1=36, d2=20` 量化步长权衡。默认参数下肉眼基本看不出，但**纯色/平滑区域可能出现轻微块状噪声** |
| **嵌入容量上限** | 每 4×4 DCT 块藏 1 bit，块数 ≈ `(W/8)×(H/8)`。例：1616×1078 → 约 **13,600 bit ≈ 1.7 KB**（含 ×3 通道冗余后实际可用更少）。水印超过容量直接 `IndexError: 最多可嵌入xx kb信息` |
| **水印会循环铺满全图** | 水印 bit 数远小于块数时会被重复嵌入（这正是它抗裁剪的原因） |
| **提取必须知道水印长度** | `wm_shape` 是必填参数。图片水印用图片尺寸，文字水印用 bit 长度（`len(bwm.wm_bit)`）。**忘了就提不出来** |
| **密码必须成对且一致** | `password_wm`（水印置乱种子）和 `password_img`（块置乱种子）**必须在嵌入/提取时完全相同** |
| **编解码版本必须一致** | 库自己会提示 `Make sure the version is the same when encode and decode`。**exe 升级后旧图可能解不出**，产品必须锁定 0.4.4 |
| **抗攻击范围** | 作者自带测试集 `att.py`：抗**截图、裁剪、旋转、缩放、亮度、椒盐噪声、遮挡**。你的笔记写"仅截图/裁剪/旋转有效，遮挡无效"——这与上游最新版有出入，建议以实测为准（见第九节待办） |
| **纯文本水印更鲁棒** | 文字水印走 k-means 二分类判定，比图片水印（逐像素阈值）抗干扰更强 |

## 六、打包方案对比与选型建议

| 方案 | 体积 | 启动 | 兼容性 | 评价 |
|---|---|---|---|---|
| **PyInstaller onefile（本次采用）** | 单 exe 60.3 MB | 3~8 s（每次解压到 `%TEMP%`） | 最好，最主流 | ✅ 推荐：拷贝即用，最符合"独立 exe"的期待 |
| PyInstaller onedir | 文件夹 ≈ 150 MB | < 1 s | 好 | 启动快、杀软误报略低，但用户看到一堆 dll 容易误删 |
| Nuitka | 40~70 MB | 2~4 s | 需 MSVC 编译环境 | 启动稍快，但构建链重、调试麻烦，收益不明显 |
| 直接调用 `blind_watermark.exe` CLI 包壳 | 60 MB | 快 | — | 无界面，用户体验差 |

本次选 **PyInstaller onefile + `console=False`（无黑框）+ 关闭 UPX 压缩**。
关闭 UPX 是刻意的：UPX 外壳是杀软误报的重灾区。

体积构成（60.3 MB）：OpenCV 约占 40+ MB，numpy 约 15 MB，Python 运行时+Tk 约 8 MB。**再压缩空间有限**——若必须瘦身，可换 `opencv-python-headless`（约省 10 MB，但会失去 GUI 相关功能，本场景可用）。

## 七、打包配置要点（原型 `bwm_gui.spec` 已落地）

- `console=False`：GUI 不弹黑框。
- `hiddenimports`：显式声明 `blind_watermark.*`、`pywt._extensions._cwt`、`cv2`、`numpy`，避免动态导入被漏掉。
- `excludes`：排除 `matplotlib/scipy/pandas/PIL/PyQt5/PyQt6/setuptools` 等，防止体积失控。
- `upx=False`：降低误报。
- `icon`：预留位，加品牌图标时填 `app.ico`。
- 打包环境用 `python -m venv --system-site-packages` 复用本机已装好的 cv2/numpy（**避免重新下载几百 MB**）。

## 八、从"能跑的原型"到"能交付的软件"还差什么

按优先级：

1. **异常兜底全覆盖**：错误密码、容量溢出、非图片文件、被截断的图、只读输出目录、超大图内存不足。
2. **水印信息随图保存**：嵌入后自动生成同名 `.txt`/sidecar（记录密码提示、bit 长度、版本号）。**这是体验提升最大的一点**——否则用户第二天必然提不出来。
3. **批量处理**：多选图片 / 整个文件夹，进度条 + 取消按钮（当前是线程 + 日志，扩起来不难）。
4. **鲁棒性一键增强**：集成 `recover.py` 的旋转/截图校正，让"被截图的图"能自动纠偏后再提取。
5. **界面打磨**：图标、关于页、拖拽文件、记住上次密码（可选，加密存储）。
6. **签名**：买 OV/EV 代码签名证书（约 ¥1000~3000/年）。**不做签名，首次运行必被 SmartScreen 警告"未知发布者"**。
7. **体积与体验二选一**：接受 onefile 3~8 s 启动，或改 onedir 换秒开。

## 九、你现有文件里发现的两个问题（顺带纠正）

1. **`嵌入提取代码.txt` 里的 `wm_shape=(128, 128)` 是错的。**
   我实际读取 `pic\watermark.png` 的尺寸是 **100×100**（`extract.py` 里的 `(100,100)` 才是对的）。用 128×128 提取会得到噪声图 —— 这大概就是你笔记里说"提取无效"的原因之一。
2. 我用正确参数 `(100,100)` 去提取你桌面已有的 `output\embedded.png`，**相关性只有 -0.0113（等于失败）**。
   说明那张 `embedded.png` 很可能**不是用 `password_wm=1, password_img=1` 生成的**（你有多个脚本、密码分别是 1 和 123），或者是被重新保存/压缩过。建议用当前脚本重新生成一张干净的样本，作为对照基准。
3. `watermark-text.py` 文件名带 "text" 但其实做的是**图片水印**（`read_wm('pic/watermark.png')` 是默认 `mode='img'`），容易误导。

## 十、最终结论

**可行性：高。** 这不是"能不能"的问题，而是"打磨多久"的问题。项目纯 Python、依赖全是成熟轮子、算法无需 GPU/网络/数据库，**PyInstaller 一次成型**。本次已产出可双击运行、中文路径无误、功能自检 PASS 的 60.3 MB 单文件 exe。

> **进度更新（v0.2 已完成）**：界面与交互已按"三个面板互不影响 / 响应式 / 傻瓜式 / 拖拽 / 默认输出路径"重构，
> 并额外修掉两个真实 bug，成品 exe 为 **61.1 MB**。详见同目录 `v0.2界面优化说明.md`。
> 端到端点击链路测试 `FLOW_TEST=PASS`，打包产物自检 `SELF_TEST=PASS`（含拖拽链路验证）。


**真正的风险不在打包，而在这三件事**：
1. 算法固有限制（容量、必须记住密码与水印长度、PNG 无损、版本锁定）→ 要靠产品设计和引导消化；
2. 无代码签名 → 首次运行会被拦截；
3. 非技术用户的预期管理 → 用户会以为"能抗一切攻击"，实际有边界（尤其中文用户经常拿微信压缩图来试，那必然失败）。
